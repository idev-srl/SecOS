# M7 Devlog — Ring-3 Entry + SYS_YIELD Cooperative Scheduling

**Branch:** `milestone/M7`
**Tag:** `M7_STABLE` (cooperative ring-3 scheduling working)
**Status:** COMPLETE (cooperative stage)

---

## Summary

M7 wires the M6 trapframe machinery into a real ring-0 → ring-3 transition and a
cooperative scheduler driven by `SYS_YIELD`. Two ring-3 processes built from a
synthetic ELF (`mov rax,0 / int 0x80 / jmp loop`) now run in user mode and hand
control back and forth via the syscall path.

The first committed version (`73a45db`) did not run: the demo stalled and the
shell was unreachable. Diagnosis uncovered **four independent bugs**, all now
fixed.

---

## Bugs found and fixed

1. **Premature timer preemption.** `sched_on_timer_tick()` called `sched_yield()`
   → `arch_switch_to_process()` (which `iretq`s and never returns) on *every*
   timer tick. As soon as the first process with a trapframe existed, IRQ0
   hijacked kernel initialization and jumped into a half-built process.
   *Fix:* the timer tick only accounts CPU time at this stage; switching is
   driven solely by `SYS_YIELD`. Preemptive scheduling is deferred to M8.
   (`kernel/sched.c`)

2. **`EFLAGS.NT` set → `iretq` #GP(0).** In long mode, executing `iretq` while
   the Nested-Task flag is set attempts an (illegal) task return and faults with
   `#GP(0)` — regardless of the iret frame. NT was left set by the boot path, so
   *every* direct `iretq` to user mode faulted. (Interrupt entry clears NT, which
   is why the timer-driven path appeared to get further.)
   *Fix:* clear `EFLAGS.NT` in `arch_iret_to_tf` — the single choke point for all
   iretq-based transitions. (`arch/x86/context_switch_asm.asm`)

3. **User `PML4[0]` supervisor + shared kernel PDPT.** `USER_CODE_BASE` (4 GB)
   and `USER_STACK_TOP` (16 GB) both fall in `PML4[0]` — the same slot as the
   kernel low identity map (0–512 MB). `vmm_space_create_user()` copied kernel
   PML4 entries with USER stripped, so `PML4[0]` was supervisor → ring-3 could
   not reach its own USER leaves (instruction-fetch #PF, `err=0x15`). It also
   *shared* the kernel's PDPT, colliding user tables across processes.
   *Fix:* give each user space its own private PDPT for `PML4[0]` — kernel low
   entries copied as supervisor, user-range PDPT slots left empty for the loader,
   and `PML4[0]` marked USER (kernel pages stay supervisor at their own level, so
   ring-3 still cannot touch them). (`mm/vmm.c`)

4. **ELF segment copy wrote at a 2× stride.** `vmm_translate_in_space()` returns
   `frame_base | (va & 0xFFF)` (offset already included), but the loader did
   `dst[va & 0xFFF] = src[off]`, adding the offset a second time. The user code
   landed as `48 00 C7 00 C0 …` instead of `48 C7 C0 …`, so ring-3 executed
   garbage and faulted.
   *Fix:* write directly to `phys_to_virt(phys)` without re-indexing. (`mm/elf.c`)

---

## Result

With `M7_RING3_DEMO=1`, two ring-3 processes alternate indefinitely:

```
[SYSCALL] pid=1 num=0   →  [SCHED] switch 1 -> 2
[SYSCALL] pid=2 num=0   →  [SCHED] switch 2 -> 1
...
```

Hundreds of thousands of clean context switches per run, both directions, no CPU
exception, no triple fault on both MB2 and UEFI.

## Gating and verification

- The demo is **off by default** (`M7_RING3_DEMO=0`) so normal boot reaches the
  interactive shell; the M4 isolation selftest still runs (12/12 PASS).
- `tools/selftest.sh` is the new non-interactive harness: it builds with the
  demo on and asserts, from the debugcon log alone, M4 12/12 + alternating
  ring-3 switches + no `[EXC]`. This is the gate for autonomous development.
- CPU exceptions are now surfaced on debugcon (`[EXC] int=… rip=…`) for headless
  crash diagnosis. (`kernel/panic.c`)
- `CFLAGS_EXTRA` is now wired into the Makefile so build-time flags
  (`M7_RING3_DEMO`, `M4_SELFTEST_ENABLE`) actually take effect.
