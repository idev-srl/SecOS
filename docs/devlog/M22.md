# M22 — NVMe storage + USB stack (xHCI + HID keyboard + Mass Storage)

**State:** done. Self-test harness **112/112** (was 102/102; +4 M22 NVMe, +6 M22
USB). Always-on (no gate): the NVMe and xHCI probes run at boot and are no-ops
when their controllers are absent.

## Goal

Cover the two device classes a modern laptop / VM actually exposes once SATA is
not enough:

1. **NVMe** — the storage controller on NVMe-only laptops and the VMware "NVMe"
   disk option. Same `block_dev_t` shape as AHCI/virtio-blk, so FAT32/ext2/ext4
   plug in unchanged.
2. **USB** — a real **xHCI** host controller plus enough of the **USB core** to
   enumerate devices and bind two class drivers: a **HID boot keyboard** (so the
   shell is usable on hardware with no PS/2 port) and **Bulk-Only Mass Storage**
   (USB sticks → `/mnt`). Booting *from* USB is the firmware's job; this is about
   *using* USB devices after boot.

Everything is **polled** and runs one operation at a time, matching the existing
AHCI/virtio-blk drivers — no IRQ wiring, no per-device threads.

## What landed

### PCI: 64-bit BARs — `drivers/pci.{c,h}`
`pci_bar_mem64(d, idx)` reads a full 64-bit memory BAR (high half from
`BAR[idx+1]` when the type bits mark it 64-bit). NVMe's register BAR (BAR0) and
xHCI's MMIO BAR (BAR0) are both 64-bit, unlike AHCI's 32-bit ABAR.

### NVMe driver — `drivers/nvme.{c,h}` (new)
PCI class **01/08/02**. Maps BAR0 through the physmap (`vmm_extend_physmap`),
reads `CAP` (doorbell stride), then the standard bring-up:
- disable (`CC.EN=0`), program the **admin** queue pair (`AQA`/`ASQ`/`ACQ`),
  enable with `IOSQES=6`/`IOCQES=4`, wait `CSTS.RDY`.
- `IDENTIFY` controller (CNS=1) then namespace 1 (CNS=0); parse `NSZE` +
  `FLBAS`/`LBAF` for sector count and size (`2^LBADS`).
- create one **I/O** queue pair (Create I/O CQ then SQ).
- read/write via `NVM READ`/`WRITE` on the I/O SQ, **polled** on the completion
  queue (phase-bit tracked, head doorbell rung). Data bounces through a static
  64 KB page-aligned buffer described by **PRP1 + a PRP-list page** (≤4 KB → PRP1
  only; ≤8 KB → PRP1+PRP2; larger → PRP list).

Registered as `block_dev_t` **"nvme0n1"**.

### xHCI host controller — `drivers/xhci.{c,h}` (new)
PCI class **0C/03/30**. The hard part. One **command ring**, one **event ring**
(single ERST segment), a **DCBAA**, and scratchpad buffers; each device gets an
**EP0 ring** plus up to `XHCI_EPR_PER_DEV` data-endpoint rings. Bring-up: reset
(`HCRST`), wait `CNR` clear, program DCBAAP/CRCR/ERST, set `CONFIG`, `RS=1`.
Per device: **port reset** → **Enable Slot** → **Address Device** (build the
input context: slot + EP0). Transfer primitives:
- `xhci_control` — SETUP / optional DATA / STATUS stage TRBs on EP0.
- `xhci_set_ep0_mps` — Evaluate Context, to fix EP0 max-packet on full/low speed.
- `xhci_configure_endpoints` — one Configure Endpoint command installing the
  interface's bulk/interrupt endpoints, each with a fresh transfer ring.
- `xhci_transfer` (blocking) and `xhci_submit`/`xhci_poll_transfer`
  (non-blocking, for the keyboard) — Normal TRBs, completion found by draining
  the event ring (context size 32 **or** 64 honoured via `HCCPARAMS1.CSZ`).

### USB core — `drivers/usb.{c,h}` (new)
Standard enumeration over the xHCI control primitives: device descriptor (fixing
EP0 MPS on FS/LS), full configuration descriptor, walk interface + endpoints,
`SET_CONFIGURATION`, Configure Endpoint, then bind a class driver by interface
class — HID boot keyboard (`03/01/01`) or SCSI Bulk-Only MSC (`08/06/50`).

### USB HID boot keyboard — `drivers/usb_hid.c` (new)
Forces boot protocol (`SET_PROTOCOL 0`), keeps **one 8-byte boot report
outstanding** on the interrupt-IN endpoint, and `usb_hid_poll()` non-blockingly
checks for completion, does **key-down edge detection** vs the previous report,
translates HID usages → ASCII (shift/caps), and injects via the new
`keyboard_inject_char()` into the **shared keyboard buffer** — so the existing
shell input path works transparently. Polled from `keyboard_has_char()` (the
input-wait path), **never from an ISR**, so it never races the event ring against
an in-flight MSC/control transfer.

### USB Mass Storage — `drivers/usb_msc.c` (new)
Bulk-Only Transport (CBW/CSW) + SCSI: **Get Max LUN** (class request),
INQUIRY, TEST UNIT READY (with REQUEST SENSE to clear the power-on Unit
Attention), READ CAPACITY(10), and READ(10)/WRITE(10) over the bulk endpoints
(32 KB chunks). Registered as `block_dev_t` **"usb0"**.

**BOT error recovery** (for real devices — QEMU never stalls): a STALL on a bulk
endpoint is recovered via `xhci_reset_endpoint` (xHC **Reset Endpoint** + ring
reset + **Set TR Dequeue Pointer**) followed by `CLEAR_FEATURE(ENDPOINT_HALT)` on
the device; a stalled data phase still proceeds to read the CSW, and a stalled
CSW phase is retried once. `xhci_last_cc()` exposes the last completion code so
the class driver can tell a STALL (`XHCI_CC_STALL`) from a fatal error.

### Block-device diagnostics — `kernel/shell.c`, `fs/block.{c,h}`
`blk` lists every detected block device (name, sector size, capacity, a sector-0
FAT/ext/GPT probe) and `mountdev <dev> [mp]` retries a FAT32/ext mount of a named
device. Both print to the **shell** (serial/framebuffer), so storage detection is
diagnosable on VMware/hardware where the debugcon markers aren't visible. Adds
`block_count()`/`block_get()`.

### Integration — `kernel/kernel.c`
`usb_init()` (xHCI + enumerate) runs at boot alongside `ahci_init`/`nvme_init`.
The boot mount tries every back-end: **`vda, sda..sdd, nvme0n1, usb0`** — the
first volume that holds a FAT32/extN filesystem is mounted at `/mnt`.

## Verification

- **NVMe** (QEMU `-machine q35 -boot d -device nvme`): `[NVME] ready nvme0n1
  sectsz=0x200 sectors=0x20000`, FAT32 mounts, `read /mnt hello` returns the
  host-written bytes, `disk write+readback: OK`.
- **USB** (`-device qemu-xhci -device usb-kbd -device usb-storage`): `[XHCI]
  running` (64 slots, 8 ports), both devices addressed, `[HID] boot keyboard
  ready`, `[MSC] usb0 ready`, FAT32 mounts on `usb0` with write+readback OK.
- **HID keystrokes end-to-end**: driving QEMU `sendkey` over the monitor, the
  injected keys decode exactly to the characters typed and reach the shell input
  buffer (verified with a temporary `HID_DEBUG_INJECT` marker).
- Both `smoke.sh --mb2` and `--uefi` still PASS (probes report "no controller"
  gracefully when absent). Self-test **112/112**.

## Follow-ups merged (additive, ⚠️ NOT YET TESTED on real hardware)

- **USB hub support** (`drivers/usb_hub.c` + xHCI routing in `xhci.{c,h}`,
  `usb.c`): enumerate devices behind a hub. New `usb_device_t` routing fields
  (route string, root port, parent hub slot/port, tier); the Enable Slot + Address
  Device body was refactored into a shared helper so root and hub-routed devices
  share it (root path byte-for-byte unchanged). `xhci_attach_hub_device()` +
  `xhci_route_append()`; the hub driver powers/resets downstream ports and
  recurses. Dormant in QEMU CI (no hub device) — emits `[HUB]` markers when found.
- **MSI / MSI-X plumbing** (`drivers/pci.{c,h}`, `arch/x86/lapic.{c,h}`, IDT
  vectors 0x40/0x41, `xhci_enable_irq`/`nvme_enable_irq`): additive and **OFF by
  default** — the kernel stays 100% polled. Device-side cap programming + LAPIC
  enable/EOI + ISR stubs are real; the interrupt path is gated behind
  `-DXHCI_USE_IRQ`/`-DNVME_USE_IRQ` and needs the LAPIC + hardware validation
  (NVMe I/O CQ still IEN=0). Default build is behaviourally identical (no `[MSIX]`).
  Self-test stays 112/112.

## Notes / gotchas

- **SeaBIOS hangs trying to boot an NVMe/USB *data* disk** (it has a filesystem
  but no boot record), so the ISO smoke runs use **`-boot d`** to force CD boot.
  This is a test-harness detail, not a kernel issue.
- **OVMF 6.2 + `-device nvme` + the `fat:rw:dist/` virtual FAT** fails to launch
  our EFI app (firmware enumeration interaction); test NVMe via the ISO/`-boot d`
  path or a real GPT/ESP disk image.
- The HID poll deliberately lives on the input-wait path, not the timer ISR, to
  keep the single shared event ring consistent with the blocking MSC/control
  transfers (no reentrancy on a single CPU).
- **Deferred** (future): NVMe/xHCI **interrupts** (MSI-X) instead of polling; USB
  hubs (only root-port devices today); multi-LUN MSC; USB3 warm reset edge cases;
  more than one keyboard.
