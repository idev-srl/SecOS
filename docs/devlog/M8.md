# M8 Devlog — Preemptive Multitasking + Process Lifecycle

**Branch:** `milestone/M7` (continues the timeline)
**Tag:** —
**Status:** CORE COMPLETE (N=2 verified); a multi-process edge case (N≥3) is a known issue

---

## Summary

M8 turns the M6/M7 trapframe machinery into a real preemptive scheduler with a
process lifecycle:

- **Preemptive scheduling.** `isr_timer` now builds a canonical `trapframe_t`
  and calls `timer_handler(tf)`. The scheduler preempts the running user task
  every `SCHED_QUANTUM_TICKS` (3 ticks at 1 kHz), saving its trapframe and
  switching to the next runnable task. It only preempts when the interrupt hit
  ring-3 (never mid-syscall in ring-0), and EOIs the PIC before the switch.
- **Kernel idle task.** A ring-0 idle task is the always-available fallback when
  no user process is runnable. Switching to it uses the same `arch_iret_to_tf`
  path (ring-0 → ring-0, which works since the M7 NT fix). The idle task reaps
  zombies and, in the demo, checks for PMM leaks.
- **`SYS_EXIT` + reaping.** `SYS_EXIT` marks the caller `PROC_ZOMBIE` and
  switches away (it can't free its own kernel stack). Zombies are reaped later
  from the idle/scheduler context (`sched_reap_zombies` → `process_destroy`).
- **Full address-space teardown.** `process_destroy` now calls
  `vmm_space_destroy`, which was fixed to free the per-process **private
  `PML4[0]` PDPT** introduced in M7 (previously assumed shared with the kernel
  and leaked). User frames, page-table frames, kernel stack, trapframe and PCB
  are all reclaimed.
- **Construction race fix.** A process is `PROC_BLOCKED` while being built and
  only promoted to `PROC_NEW` once its trapframe is ready, so the preemptive
  scheduler cannot pick a half-initialized process.

The serial console (the other M8 deliverable) already shipped in M7.

## Verification

The M8 demo (`-DM8_SCHED_DEMO=1`) creates N user processes that compute then
`SYS_EXIT`, runs several spawn-all/exit-all rounds, and has the idle task assert
PMM free is identical across the last two rounds (stable ⇒ no per-round leak).

With **N=2**, all rounds pass on the smoke harness:
```
[SCHED] preempt 1 -> 2 ...        (timer-driven preemption)
[SCHED] exit 1 / exit 2 ...       (SYS_EXIT)
[M8] PMM stable across rounds: NO LEAK
[M8] DONE
```
`tools/selftest.sh` asserts: ≥2 preemptive switches, ≥4 `SYS_EXIT`, `NO LEAK`,
`[M8] DONE`, and no CPU exception. The demo is gated (off by default), so normal
boot still reaches the shell.

## Known issue — N ≥ 3 spawn corruption

With three or more processes spawned in a round, after a couple of rounds a
just-created process's `PML4[0]` entry is observed zeroed (its code becomes
unmapped) when the *next* process in the same round is created — the process
then spins in ring-3 and the run stalls. Investigation established:

- It is **not** a PMM double-free or double-alloc (the bitmap allocator no-ops
  double frees; the victim frame is allocated exactly once and never freed in
  the window), and **not** `zero_frame`, `vmm_unmap_in_space`, `m2_mark_guard`,
  or any physmap-routed table write (all watched, none fired).
- The victim PML4 entry is overwritten via some path that does not go through
  the physmap — most likely an identity-mapped low-address write — only once
  enough frame churn has accumulated (N=1 and N=2 are stable across many rounds).

This points at a frame-aliasing/identity-mapping issue rather than the scheduler
itself, and is the first investigation item for **M9** (which reworks the PMM
and higher-half/identity mapping anyway). Until then the demo uses N=2.
