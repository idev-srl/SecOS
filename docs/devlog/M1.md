## M1.4 – Stabilizzazione timing GDT/TSS

**Commit**: `73d79fe [M1][GDT] Stabilize TSS initialization timing`

### Problema
`tss_init()` veniva chiamato DOPO `idt_init()`. `idt_init()` termina con `sti` e registra
gate #DF (IST=1), #PF (IST=2), #GP (IST=3). Tra `idt_init()` e `tss_init()`:
- TR (Task Register) non inizializzato — `_uefi_start` ricarica la GDT di boot (3 entry, no TSS) ma non esegue `ltr`
- IST stacks non ancora allocati
- `vmm_init_physmap()` girava con interrupt attivi e senza TSS valido

Qualsiasi #PF/#GP/#DF tra `idt_init()` e `tss_init()` avrebbe causato triple fault silenzioso.

### Fix (kernel/kernel.c)
```
PRIMA:  vmm_init() → idt_init() → vmm_init_physmap() → tss_init()
DOPO:   vmm_init() → tss_init() → idt_init() → vmm_init_physmap()
```

Dipendenze soddisfatte: `tss_init()` richiede solo PMM (già inizializzato prima di `vmm_init()`).

### Verifica
QEMU exit code 124 (timeout kill) su run da 5s e 25s → kernel alive, no regressioni.

## M1.1 – Kernel-owned page tables + CR3 switch

**Commit**: in corso

### Obiettivo
Costruire PML4/PDPT/PDT kernel-owned tramite PMM, replicando il mapping identità 0–512MB
a pagine da 2MB. Caricare il nuovo CR3. Il kernel deve continuare a girare normalmente dopo lo switch.

**Invariante obbligatorio**: il mapping identità 0–512MB rimane SEMPRE presente
(richiesto da tutte le funzioni VMM che usano `(uint64_t*)phys` direttamente).

### Analisi pre-modifica

**`vmm_init()` originale** (`mm/vmm.c:136-143`):
```c
void vmm_init(void) {
    kernel_space.pml4_phys = read_cr3();  // eredita tabelle del bootloader
    // ... solo stampa CR3
}
```

Il kernel ereditava le tabelle UEFI (frame `AllocatePages`), potenzialmente riciclabili
da PMM in futuro.

**Identità cast pervasivi** (`get_pt_space`, `get_or_create_table`, `vmm_init_physmap`):
tutti usano `(uint64_t*)pml4_phys` assumendo identità — richiedono che 0–512MB rimanga mappato.

**Sicurezza dello switch**:
- Frame PMM allocati sono entro 0–128MB (capped da PMM) → coperti dall'identità sia
  vecchia che nuova
- `zero_frame()` usa fallback identità (`physmap_initialized == 0` durante `vmm_init()`)
- Dopo `write_cr3(new_pml4)` l'esecuzione continua allo stesso indirizzo virtuale
  (0x200000+), presente identicamente nelle nuove tabelle ✓

### Modifiche applicate (`mm/vmm.c`)

**Nuova funzione statica** `vmm_build_kernel_pml4_identity_512mb()`:
```c
static uint64_t vmm_build_kernel_pml4_identity_512mb(void) {
    // Alloca 3 frame da PMM: PML4, PDPT, PDT
    // Azzera con zero_frame() (identity fallback, physmap non attiva)
    // PML4[0] = pdpt_phys | P|W
    // PDPT[0] = pdt_phys  | P|W
    // PDT[0..255] = (i << 21) | P|W|PS  → 256 × 2MB = 512MB identità
    // Restituisce pml4_phys
}
```

**`vmm_init()` modificato**:
```c
void vmm_init(void) {
    old_cr3 = read_cr3();           // stampa bootloader CR3
    new_pml4 = vmm_build_kernel_pml4_identity_512mb();
    write_cr3(new_pml4);            // switch atomico
    kernel_space.pml4_phys = new_pml4;
    // sanity read: legge kernel_space.pml4_phys attraverso le nuove tabelle
}
```

**Fallback**: se PMM alloc fallisce → stampa warn e mantiene bootloader CR3.

### Ordine di init aggiornato (`kernel/kernel.c`)
```
pmm_init_uefi()         → PMM pronto
vmm_init()              → build tabelle kernel-owned + CR3 switch    ← M1.1
tss_init()              → GDT+TSS+IST stacks (usa PMM post-switch)
idt_init()              → IDT + STI (IST stacks validi)
vmm_init_physmap()      → physmap in nuove tabelle kernel-owned
```

### CR3 prima e dopo lo switch

| | CR3 | Frame | Origine |
|---|-----|-------|---------|
| **Bootloader** | valore UEFI AllocatePages | firmware-managed | `efi_main` in `uefi/boot.c` |
| **Kernel (M1.1)** | ~0x22E000 (primo frame libero post-kernel+bitmap) | PMM-owned | `vmm_build_kernel_pml4_identity_512mb()` |

*Nota*: il valore esatto del nuovo CR3 dipende dal layout PMM al momento dell'allocazione.
Con kernel segment size 0x2C940 (da log UEFI), `_kernel_end` ≈ 0x22C940, bitmap ≈ 4KB,
primo frame libero ≈ 0x22E000 → PML4 a 0x22E000, PDPT a 0x22F000, PDT a 0x230000.

### QEMU smoke test

```bash
qemu-system-x86_64 \
  -machine pc -cpu qemu64 -m 512M \
  -drive if=pflash,format=raw,readonly=on,file=/usr/share/OVMF/OVMF_CODE.fd \
  -drive if=pflash,format=raw,file=dist/OVMF_VARS_test.fd \
  -drive if=ide,format=raw,file=dist/test_esp.img \
  -serial file:/tmp/M1_uefi_smoke.log \
  -debugcon file:/tmp/M1_uefi_debug.log \
  -display none -no-reboot
```

**Risultato**: exit code 124 (timeout 20s) → kernel alive.
Con `-no-reboot`, un triple fault causa uscita immediata di QEMU (exit ≠ 124).

### Stato tabelle dopo M1.1

```
PML4 kernel-owned (PMM frame ~0x22E000):
  [0]   → PDPT (~0x22F000) | P|W
    [0] → PDT  (~0x230000) | P|W
      [0..255] → phys i*2MB | P|W|PS   (identità 0–512MB, 2MB pages)
  [272] → (vuoto, popolato da vmm_init_physmap)
```

Le funzioni VMM esistenti (`get_pt_space`, `vmm_init_physmap`, ecc.) continuano
a funzionare invariate: usano `(uint64_t*)pml4_phys` che è ancora valido sotto
l'identità mantenuta.

## M1.2 – Physmap-aware page table walkers

**Commit**: in corso

### Obiettivo
Rimuovere la dipendenza permanente dall'identity mapping nei walker di page table
*dopo* che physmap è inizializzata. Ogni dereferenziazione di un frame di page table
deve usare `phys_to_virt(phys)` quando `physmap_initialized == 1`.

**Invariante M1.2**: l'identity mapping 0–512MB NON viene rimosso. Rimane presente
nelle tabelle kernel-owned per tutta la durata di M1.2 e oltre.

### Motivazione tecnica

Quando `vmm_init_physmap()` costruisce il physmap, può allocare frame PDT/PDPT per
indirizzi fisici > 512MB (se la RAM è più grande). Quei frame sono accessibili solo
tramite physmap, non tramite identity. Se i walker di page table usassero `(uint64_t*)phys`
su frame al di sopra di 512MB, causerebbero accessi a memoria non mappata → #PF.

Con la PMM attualmente cappata a 128MB non si manifesta con la RAM di test (128MB < 512MB),
ma è un bug latente: basta aumentare la RAM o rimuovere il cap in M2.

### Siti critici modificati (`mm/vmm.c`)

#### 1. `get_or_create_table()` (linea ~88)

**Prima**:
```c
return (uint64_t*)phys; // Identity assumption
...
return (uint64_t*)(entry & ADDRESS_MASK);
```

**Dopo**:
```c
// path new allocation:
if (physmap_initialized) { return (uint64_t*)phys_to_virt(phys); }
return (uint64_t*)phys;
// path existing entry:
return physmap_initialized ? (uint64_t*)phys_to_virt(phys) : (uint64_t*)phys;
```

Aggiunto one-shot debug print alla prima invocazione del path `phys_to_virt`.

#### 2. `get_pt_space()` (linea ~102)

**Prima**:
```c
uint64_t* pml4 = (uint64_t*)pml4_phys; // Identity assumption
uint64_t* pdpt = (uint64_t*)(pml4[pml4_i] & ADDRESS_MASK);
uint64_t* pdt  = (uint64_t*)(pdpt[pdpt_i] & ADDRESS_MASK);
uint64_t* pt   = (uint64_t*)(pdt[pdt_i]   & ADDRESS_MASK);
```

**Dopo**: tutti i cast fisici convertiti a:
```c
uint64_t* pml4 = physmap_initialized ? (uint64_t*)phys_to_virt(pml4_phys) : (uint64_t*)pml4_phys;
// per ogni livello presente:
uint64_t pdpt_phys = pml4[pml4_i] & ADDRESS_MASK;
pdpt = physmap_initialized ? (uint64_t*)phys_to_virt(pdpt_phys) : (uint64_t*)pdpt_phys;
// idem per PDT e PT
```

Path "crea nuovo entry" delegata a `get_or_create_table` già corretta.

#### 3. `vmm_extend_physmap()` (linea ~29)

Questa funzione viene chiamata SOLO quando `physmap_initialized == 1` (check a riga 30).
Quindi tutti i cast interni sono stati convertiti a `phys_to_virt` incondizionati:

```c
uint64_t* pml4 = (uint64_t*)phys_to_virt(pml4_phys);
uint64_t* pdpt = (uint64_t*)phys_to_virt(pml4[pml4_i] & ADDRESS_MASK);
// nell'inner loop:
pdt = (uint64_t*)phys_to_virt((uint64_t)frame & ADDRESS_MASK);  // nuova PDT
pdt = (uint64_t*)phys_to_virt(pdpt[pdpt_i] & ADDRESS_MASK);    // PDT esistente
```

#### 4. `vmm_init_physmap()` — instrumentazione

Nessun cambio ai cast interni (la funzione gira con `physmap_initialized == 0` fino
alla fine). Aggiunto print diagnostico dopo `physmap_initialized = 1`:

```c
terminal_writestring("[M1.2] physmap_initialized=1. phys_to_virt(0x200000)= 0xFFFF888000200000\n");
```

### Cosa NON è stato modificato (fuori scope M1.2)

- `ensure_pt_for_identity()` — usata solo da `vmm_protect_kernel_sections` (non chiamata
  nel boot path attuale)
- `vmm_space_create_user()` / `vmm_harden_user_space()` — user space, scope M1.5+
- `vmm_init_physmap()` walk interno — gira sotto identity, non necessita modifica

### Verifica

```bash
qemu-system-x86_64 \
  -machine pc -cpu qemu64 -m 512M \
  -drive if=pflash,format=raw,readonly=on,file=/usr/share/OVMF/OVMF_CODE.fd \
  -drive if=pflash,format=raw,file=dist/OVMF_VARS_test.fd \
  -drive if=ide,format=raw,file=dist/test_esp.img \
  -serial file:/tmp/M1_2_uefi_smoke.log \
  -debugcon file:/tmp/M1_2_uefi_debug.log \
  -display none -no-reboot
```

**Risultato**: QEMU exit code 124 (timeout 20s). Kernel alive, nessun triple fault.
UEFI chain completa fino a ExitBootServices (confermato in log seriale).
I print `[M1.2]` vengono emessi sul terminale VGA (non catturabili via serial senza
abilitare output seriale kernel).

### Dipendenze sull'identity mapping ancora presenti dopo M1.2

- `vmm_init_physmap()` internal walk (gira sotto identity, accettabile)
- `vmm_build_kernel_pml4_identity_512mb()` in M1.1 (gira pre-physmap, corretto)
- `ensure_pt_for_identity()` / `vmm_space_create_user()` (non nel boot path attivo)

## M1.3 – Guard pages + linker COMMON fix + IST stacks

**Commit**: in corso

### Deliverables

#### D) linker.ld fix (`linker.ld`)

**Bug**: `*(COMMON)` era posizionato PRIMA di `_bss_start`, lasciando simboli COMMON fuori
dal range `[_bss_start, _bss_end]` protetto da W^X.

**Fix**: spostato `*(COMMON)` dopo `_bss_start = .;`

#### A) Kernel stack guard page (`mm/vmm.c`)

Nuova funzione statica `vmm_install_guard_page(uint64_t guard_virt)`:
1. Walk PML4 → PDPT → PDT usando `phys_to_virt` (post-physmap)
2. Se PDE è huge (2MB, flag PS), split in 512 × 4KB PTE
3. Mark PTE per `guard_virt` come not-present (= 0)
4. `invlpg` per invalidare TLB

`vmm_setup_kernel_guard_pages()` chiama `vmm_install_guard_page(stack_bottom - PAGE_SIZE)`.

#### C) IST stacks aumentati + guard pages (`arch/x86/tss.c`, `mm/vmm.c`)

- `IST_STACK_SIZE` aumentato da 4KB a 8KB (2 frame consecutivi per IST)
- Aggiunto `tss_get_ist_bases()` per esporre i base address degli IST stack
- `vmm_setup_kernel_guard_pages()` installa guard page sotto ogni IST stack base

#### B) User stack guard page esplicito (`mm/vmm.c`)

`vmm_alloc_user_stack()` e `vmm_alloc_user_stack_in_space()` ora creano esplicitamente
la PTE della guard page (create=1) e la settano a 0 (not-present), invece di dipendere
dall'assenza implicita del mapping.

### Init order aggiornato (`kernel/kernel.c`)

```
pmm_init_uefi()                → PMM pronto
vmm_init()                     → kernel-owned page tables + CR3 switch
tss_init()                     → GDT + TSS + IST stacks (8KB ciascuno)
idt_init()                     → IDT + STI
vmm_init_physmap()             → physmap nelle nuove tabelle kernel-owned
vmm_setup_kernel_guard_pages() → guard pages kernel stack + IST    ← M1.3
```

### Verifica

QEMU exit code 124 (timeout 20s) → kernel alive, nessun triple fault.
