# M27a — JBD2 journal replay (crash recovery, read-side)

_Status: code complete, build clean, verified against an **e2fsck-validated**
synthetic dirty journal (root-free). First half of Phase H part 2 (crash
consistency). M27b — write-side journaling so SecOS's **own** writes are
crash-safe — is the larger remaining piece and is deferred to a follow-up._

## Goal

Make SecOS safe to mount an ext3/ext4 volume that was left **dirty** by a crash
on another OS: replay the committed-but-not-checkpointed JBD2 transactions on
mount, so we never read stale in-place metadata. (Today SecOS's own ext4 is still
"no-journal v0"; M27a is the read/recovery side, M27b the write side.)

## What landed (`fs/ext2.c`)

`jbd2_recover()` runs in `ext2_mount` / `ext2_mount_root` right after the
superblock read. It is a no-op unless the volume has `HAS_JOURNAL` (compat 0x4)
**and** the journal is non-empty (`s_start != 0`). JBD2 is **big-endian** on disk
(dedicated `be32`/`be16` readers).

Standard 3-pass recovery (mirrors Linux jbd2 / e2fsck):
1. **SCAN** — walk transactions from `s_start` at sequence `s_sequence`,
   following commit blocks, to count the committed transactions (`end_seq`). A
   descriptor whose commit is missing (the crash tail) is excluded because the
   later passes stop once `seq >= end_seq`.
2. **REVOKE** — collect revoke records (block → revoking sequence) into a table.
3. **REPLAY** — for each descriptor tag, read the journalled data block and write
   it to its final location, **unless** the block is revoked at a sequence ≥ the
   transaction's (so a freed-and-reused block isn't clobbered with stale data).
   Handles the `ESCAPE` flag (restores a data block whose first word collided
   with the JBD2 magic) and the per-tag UUID (skipped when `SAME_UUID`).

Tag formats handled: v2 (8-byte) and v3/CSUM_V3 (16-byte), with the 64-bit
block-number extension. Checksums are **not verified** (we replay regardless),
which is safe for recovery and keeps us compatible with csum-enabled journals.

After a successful replay, the journal is marked clean (`s_start = 0`,
`s_sequence = end_seq`) and the fs `NEEDS_RECOVERY` incompat flag is cleared, so
we don't recover twice and `e2fsck` afterwards sees a clean volume.

## Verification (root-free, e2fsck-validated)

The hard part of testing crash recovery without root (no loop-mount / dmsetup) is
producing a genuinely-dirty journal. `tools/mk_dirty_journal.py` synthesizes one:
it stages a single committed transaction (descriptor + data + commit) rewriting a
target file's first block from `OLD` to `NEW`, sets `s_start` + `NEEDS_RECOVERY`,
and leaves the in-place block stale. Block locations are resolved via
`debugfs bmap` (userspace). `make disk-journal` builds the image.

**Ground truth:** running `e2fsck -fy` on a *copy* replays the synthetic journal
and the target file becomes `NEW` — proving it's a real JBD2 journal, not just
"valid per our own reader". SecOS then:
```
[M27] journal recover: txns=1
[M27] target.bin n=0x3FE data="NEW"   (was "OLD" in place)
[M27] REPLAY OK
```
and `e2fsck -fn` on the post-replay image is **clean**. So SecOS's recovery
matches Linux's, independently checked. selftest adds 5 M27 cases (incl. the
e2fsck ground-truth cross-check and the post-replay fsck-clean check).

Demo gate `M27_RECOVER_DEMO` (reads `/mnt/target.bin` after mount).

## Files

- `fs/ext2.c` — `jbd2_recover()` + 3-pass `jbd2_pass()`, wired into both mount

- `tools/mk_dirty_journal.py` — e2fsck-validated synthetic dirty-journal builder.
- `Makefile` — `disk-journal` target; `kernel/kernel.c` — `M27_RECOVER_DEMO`;

# M27b — write-side journaling (crash-atomic SecOS metadata writes)

_Completes Phase H. SecOS's own filesystem mutations are now crash-atomic on a
journalled ext3/ext4 volume, proven with a fault-injection harness._

## Model (`fs/ext2.c`)

A **metadata transaction** wraps each mutating VFS op (create/mkdir/remove/rename/
truncate/setattr/symlink/write — the `e2j_*` wrappers). While a transaction is
open (`g_jt_active`):
- `blk_write()` **buffers** the block into the transaction (dedup by block number)
  instead of writing in place — metadata.
- **File data** and the zeroing of a freshly-allocated block use
  `blk_write_direct()` — written immediately (ordered mode: data reaches disk
  before the metadata commit).
- `blk_read()` is **read-your-writes**: a block already modified in this txn is
  served from the buffer, so read-modify-write of *shared* metadata (group
  descriptor, superblock, bitmaps touched by both inode and block allocation)
  accumulates instead of clobbering. _(This was the one real bug found during
  bring-up: without it, the gd/sb/bitmap updates of one op overwrote each other
  and e2fsck flagged count/bitmap drift. The legacy direct path didn't hit it
  because writes landed immediately.)_

`jt_commit()` writes the transaction to the JBD2 journal and applies it, in the
order that makes it atomic (reusing M27a's on-disk format, big-endian):
1. write the **descriptor** (one tag per buffered block; first tag carries a UUID,
   the rest `SAME_UUID`, last `LAST_TAG`) + the buffered blocks + a **commit** block;
2. **publish** — set the journal superblock `s_start`/`s_sequence` to point at the
   transaction (now it's a valid, replayable txn);
3. **checkpoint** — write the buffered blocks to their final in-place locations;
4. **retire** — `s_start = 0`, `s_sequence++`.

On **failure** the transaction is discarded (`jt_abort` — nothing reaches disk, so
the op rolls back atomically; any direct data writes landed on not-yet-referenced
blocks and are harmless). With **no journal** on the volume, transactions degrade
to plain in-place writes (legacy behaviour, byte-for-byte). Only csum-free,
non-async journals are used for writing (`jt_init` checks the journal feature
flags); a csum/async journal falls back to legacy.

## Crash-atomicity (fault-injection harness)

`g_blk_dead` simulates power loss: once set, every block write is dropped.
`jt_commit` cuts power at two precise points under test control
(`ext2_test_set_crash`): **before the commit block** and **after publish**. The
guarantee, proven by running SecOS, crashing, then booting again (recovery via
M27a) and checking on the host:

| crash point | next-mount recovery | result | e2fsck |
|---|---|---|---|
| before commit | no committed txn found | op **absent** (old state) | clean |
| after publish | committed txn **replayed** | op **present** (new state) | clean |

Never a torn/half-applied state. Demo gates `M27B_CRASH=1|2` (run 1, crash) +
`M27B_VERIFY` (run 2, recover & report). selftest adds the baseline (journalled
write is e2fsck-clean) + both crash scenarios.

## Scope notes
- **Ordered mode** (metadata journalled, data direct): a crash may lose *recent
  file data*, but the filesystem structure is always consistent — the standard
  ext3/ext4 default.
- **`metadata_csum`** is intentionally **not** implemented: SecOS journals to
  `^metadata_csum` volumes (consistent with the M10 policy) and skips journal
  checksums, so there are no csums to maintain. Full fs-wide `metadata_csum` is a
  separate, orthogonal feature and remains a follow-up.
- Transaction size is bounded (`JT_MAX=64` dedup'd metadata blocks) — ample for a
  single VFS operation; overflow degrades to a direct write.

**Phase H is complete**: `/dev`+`/proc`+`/sys` (M23), VFS metadata/symlinks/mount
(M26), journal **replay** (M27a) and **write-side crash-atomicity** (M27b).
