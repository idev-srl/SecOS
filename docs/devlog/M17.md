# M17 — Blocking primitives: sleep + blocking IPC receive

**State:** done. Self-test harness **75/75** (was 70/70; +5 M17 assertions).
Demo gated behind `M17_BLOCK_DEMO`, off by default. Phase F (process model).

## Goal

Replace busy-polling with real blocking, built on the block/wake primitive
introduced for M16's `SYS_WAIT`. Two user-visible primitives:
- `SYS_SLEEP(ticks)` — block until a timer-tick deadline (vs. spinning on `hlt`).
- `SYS_MSG_RECV` — block on an empty IPC channel until a send arrives (vs. the
  M13 non-blocking poll).

## What landed

### The block/wake core (extended from M16) — `kernel/sched.c`
`process_t` already carried `sleep_until` and `recv_chan` (added alongside the
M16 wait fields). M17 adds the two matching wakers:
- `sched_wake_sleepers(now)` — flips every `PROC_BLOCKED` process whose
  `sleep_until <= now` back to `PROC_READY`. Called every tick from
  `sched_on_timer_tick`.
- `sched_wake_chan(chan)` — wakes every process blocked receiving on `chan`.
  Called from the `SYS_MSG_SEND` path after a successful `ipc_send`.

Both reuse the M16 mechanism: a blocking syscall rewinds `rip` by 2 and calls
`sched_block_current`; on wake the syscall re-runs and re-checks its condition.

### SYS_SLEEP — `kernel/syscall_trap.c`, `kernel/syscall.h`
New syscall (13). Handled in `syscall_handler` (it blocks, so it needs the
trapframe). First entry arms `sleep_until = now + ticks` and blocks; the timer
tick wakes it once the deadline passes; the re-run sees `now >= sleep_until`,
clears it, and returns 0. libc: `void sleep_ticks(unsigned ticks)`.

### Blocking SYS_MSG_RECV — `kernel/syscall_trap.c`, `kernel/syscall.c`
`SYS_MSG_RECV` moves to `syscall_handler`. It calls `ksys_msg_recv_try` (validate +
`ipc_recv` + `copy_to_user`); on a non-empty channel it returns the bytes as
before. On an **empty** channel it arms `recv_chan`, rewinds `rip`, and blocks.
A later `SYS_MSG_SEND` calls `sched_wake_chan`, the receiver re-runs, and now
drains the message.

**Backward compatible:** a *pre-queued* message is returned on the first call
without blocking, so the M13 poll-loop consumer (and its self-test) is unchanged —
verified still green.

### Demo + harness — `kernel/kernel.c` (`M17_BLOCK_DEMO`), `user/m17_sleeper.c`
Two proofs:
1. **Sleep:** the signed `m17_sleeper` records uptime, `sleep_ticks(10)`, and
   verifies the uptime advanced by ≥ 10 — printing `[sleep] OK slept >=10`.
2. **Blocking recv ordering:** the consumer (`ipc_recv`) is spawned **first** and
   the demo waits until it is observably `PROC_BLOCKED` on channel 0 before
   spawning the producer (`ipc_send`). The producer's send wakes the blocked
   consumer, which then receives the message. Consumer-before-producer delivery is
   only possible via a real block + wake, not a poll that would have returned 0.

Five assertions, including the `[M17] consumer is BLOCKED on recv` checkpoint that
distinguishes blocking from polling.

## Things worth noting

- **Spurious wakes are safe:** `sched_wake_chan` wakes *all* receivers on a
  channel; if two race, the loser's re-run finds the channel empty again and
  re-blocks. The rip-rewind re-run model makes this automatic.
- **Sleep granularity** is the timer tick (PIT frequency). `sleep_until == 0` is
  the "not sleeping" sentinel, so a 0-tick sleep is bumped to 1.
- **No lost wakeups:** the kernel is non-preemptible, so arming the wait condition
  and blocking happen atomically with respect to a sender/timer that runs in a
  later interrupt — there is no window between "check empty" and "block".
