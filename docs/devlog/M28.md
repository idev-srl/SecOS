# M28 — Modern platform: ACPI / APIC / timekeeping (Phase I, part 1)

_Phase I is the heaviest phase (it culminates in SMP, M29 — the single biggest
correctness effort in the roadmap). It is built up in sub-steps; each is its own
verified increment._

## M28-1 — ACPI table discovery (done)

Read-only discovery of the platform topology from ACPI — the prerequisite for
retiring the 8259 PIC (APIC/IOAPIC, M28-2) and bringing up the other cores (SMP,
M29). It does **not** touch the live PIC/PIT interrupt path.

**`arch/x86/acpi.{c,h}`**:
- **RSDP**: on **UEFI** the loader now hands the RSDP over (the only reliable
  source there) — `uefi/boot.c` walks `SystemTable->ConfigurationTable` for the
  ACPI 2.0 (then 1.0) GUID before `ExitBootServices` and stores it in
  `secos_boot_info.acpi_rsdp` (new field; `efi.h` gained the config-table struct
  + GUIDs + the missing `EFI_SYSTEM_TABLE.ConfigurationTable`). On **MB2** it
  falls back to scanning the legacy BIOS area (EBDA + `0xE0000–0xFFFFF`).
- **Parse**: RSDP → XSDT (ACPI 2.0) or RSDT → find the **MADT** ("APIC") → CPU
  Local-APIC IDs + count, LAPIC base, IOAPIC(s) base+GSI-base, and interrupt
  source overrides. `acpi_irq_to_gsi()` applies the overrides (for M28-2's IOAPIC
  programming).
- ACPI tables are read through the **permanent low identity map (0–512 MiB)**,
  not the physmap: the physmap may not yet cover the ACPI region on the UEFI path
  (the tables sit near the top of RAM, e.g. ~252 MiB on a 256 MiB VM), and that
  caused a #PF until the read was routed through the identity map.

**Verified** (no `[EXC]`, scales with `-smp`):
- MB2 (BIOS scan): `[ACPI] CPUs=1 lapic=0xFEE00000 ioapics=1 ioapic0=0xFEC00000 …`
- UEFI/OVMF (RSDP via loader), `-smp 2`: `[ACPI] CPUs=2 …`

## M28-2 — APIC switchover (done)

Retire the legacy 8259 PIC + PIT IRQ0 onto the **Local APIC timer** (scheduler
tick) and the **IOAPIC** (device IRQs), driven by the M28-1 MADT topology. This
is live-interrupt surgery; it keeps a clean PIC/PIT fallback and both boot paths
green. All in **`arch/x86/lapic.c`** (which already owned the LAPIC mapping for
MSI), orchestrated by `apic_switchover(hz)`, called from `kernel_main_phase2`
right after `timer_init()/keyboard_init()`.

**What it does** (with interrupts disabled, then `sti`):
1. `lapic_enable()` — software-enable the LAPIC (SVR bit8, spurious vec 0xFF).
2. Flip the **IMCR** (`outb 0x22,0x70; outb 0x23,0x01`) so firmware that booted
   in PIC mode hands INTR to the IOAPIC (harmless no-op under QEMU).
3. **Mask the 8259** fully (OCW1 `0xFF` to `0x21` and `0xA1`).
4. **IOAPIC**: route ISA **IRQ1 → GSI** (`acpi_irq_to_gsi`, honouring MADT
   override polarity/trigger flags) to **vector 0x21** (`isr_keyboard`), physical
   delivery to the BSP LAPIC ID. (The IOAPIC MMIO is mapped via the physmap.)
5. **LAPIC timer**: calibrate against **PIT channel 2** (independent of the
   8259, still counts with the PIC masked — gate via port `0x61`, poll OUT2 on
   `0x61` bit5 over a 10 ms window, measure LAPIC-counter decay with divide /16),
   then program it **periodic at 1 kHz on vector 0x20** — the *same* vector the
   PIT used, so `isr_timer` + the IDT gate are unchanged.

**Key design choice — the vector stays 0x20.** Only the **EOI source** moves. A
new `irq_eoi()` dispatches the end-of-interrupt to the LAPIC in APIC mode, else
the 8259 master. The two `isr_timer`/`isr_keyboard` asm stubs now `call irq_eoi`
in place of the inline `out 0x20,0x20`, and the scheduler's preempt path
(`sched.c`, which EOIs itself because `switch_to()` never returns) calls
`irq_eoi()` too. So flipping `g_apic_mode` re-points every EOI atomically.

**Fallback:** if `acpi_get()` has no MADT/IOAPIC, or PIT calibration yields 0,
`apic_switchover()` returns −1 and re-enables the PIC/PIT it had masked — the
kernel runs exactly as before (`irq_eoi` stays in 8259 mode).

**Self-check:** after switchover the kernel confirms `timer_get_ticks()` actually
advances (bounded spin, never hangs boot) → `[APIC] timer tick verified`, proving
the LAPIC timer fires and IRQ delivery works end-to-end.

**Verified** (no `[EXC]`, both boot paths PASS):
- MB2 `-smp 2` and UEFI/OVMF: `[APIC] IOAPIC route irq=1 … vec=0x21` /
  `[APIC] LAPIC timer hz=0x3E8 ticks/s≈0x3BCFDD8 init≈0xF4FD` /
  `[APIC] mode active (PIC masked, LAPIC timer + IOAPIC)` / `timer tick verified`.
- **Preemption still works on the new tick**: `M8_SCHED_DEMO` shows 16×
  `[SCHED] preempt`, `[M8] PMM stable across rounds: NO LEAK`, `[M8] DONE`.
- selftest M28 section gained 4 `[APIC]` assertions.

**Gotchas / notes:**
- LAPIC timer is calibrated, not assumed: QEMU's LAPIC runs ~1 GHz, so /16 gives
  ~62.5 M ticks/s → `init` ≈ 62.5 k for 1 kHz (matches the logged value).
- `timer_init(1000)` still runs first (it sets `timer_frequency=1000`, used by
  uptime math); the PIT it programs is then masked. `timer_ticks` keeps advancing
  because the LAPIC timer drives the same `isr_timer`.
- The asm `call irq_eoi` sits where the old EOI did (same RSP as the existing
  `call timer_handler`/`call keyboard_handler`), so stack alignment is unchanged;
  the C call may clobber caller-saved regs but every GPR is restored from the
  stack immediately after.

## M28-3 — TSC timekeeping (done)

A monotonic nanosecond clock from the **TSC**, calibrated once at boot — the last
platform piece before SMP. **`arch/x86/tsc.{c,h}`**:

- **Calibration** against **PIT channel 2** (`tsc_init()`): the same gate/poll
  trick M28-2 uses (port `0x61` gate + OUT2 bit5), over a 50 ms window. Channel 2
  is not wired to the 8259, so this works in *either* interrupt mode — before or
  after the APIC switchover, with the PIC masked. `tsc_hz = cyc * PIT_HZ / count`
  (exact ratio, not a hard-coded 50 ms).
- **`ktime_ns()/us()/ms()`** monotonic since boot. Hot path is a **fixed-point
  multiply-shift**: `ns = (cycles * mult) >> 32`, where `mult` is precomputed at
  calibration with one 64-bit divide. This deliberately avoids a 128-bit *divide*
  (`__udivti3`) — libgcc is **not** linked (`-nostdlib`), so a `(__uint128_t)/hz`
  fails to link; the 64×64→128 *multiply* compiles to a native `mulq` (no helper).
  That link error was the one bring-up snag.
- **Self-check** at boot: `tsc_hz() > 100 MHz` and two `ktime_ns()` reads strictly
  increase → `[TSC] monotonic OK` (QEMU/VMware report ~2.5 GHz).
- **Wired in**: `net_tsc_per_us()` (ping RTT) now prefers the calibrated `tsc_hz()`
  instead of its own 1 kHz-timer calibration; `/proc/uptime` shows sub-second
  precision (`<sec>.<cc> s`) and `/proc/cpuinfo` gains `tsc_mhz`.

Assumes a constant/invariant TSC (true on QEMU, modern Intel/AMD, VMware); P-state
TSC variance is not handled (not relevant to the targets). `SYS_GETTICKS` is left
as the 1 kHz scheduler tick (unchanged ABI); the ns clock is kernel-internal +
exposed via procfs. Selftest M28 gained 2 `[TSC]` assertions.

**Phase I status:** parts 1–3 done (ACPI discovery, APIC switchover, TSC
timekeeping). Remaining: **M29 — SMP** (AP bring-up via LAPIC IPIs + the M28-1
CPU list; kernel-wide locking audit first). That is the single biggest correctness
effort and is best taken on in a fresh session.
