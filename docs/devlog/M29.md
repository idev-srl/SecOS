# M29 — SMP (multicore), Phase I final part

The single biggest correctness effort in the roadmap: bring up the application
processors and run user code on more than one core. Built in tested sub-steps.

**Architecture decision (locked):** instead of a Big Kernel Lock around the
context-switch path (classically the most fragile point — releasing/re-acquiring
a global lock across `iretq` into user mode and across non-returning
`switch_to()`), SecOS uses **per-CPU run state with CPU-pinned processes** plus
**fine-grained spinlocks** on the genuinely shared subsystems (PMM, heap, page
cache, VFS mount table, block I/O, IPC, pipes, keyboard). Each core only ever
schedules tasks pinned to it, so `current`/`idle`/quantum are per-CPU and the
context switch needs no lock. Cross-CPU interactions (a wake from another core)
only flip a process `state` under a lock; the owning core picks it up on its next
tick. This sidesteps the BKL-across-switch problem entirely.

## M29-1 — SMP primitives (done)

No behavioural change on a single core; lays the foundation.

- **`arch/x86/spinlock.h`** — ticket-free test-and-test-and-set spinlock with
  `spin_lock_irqsave`/`spin_unlock_irqrestore` (disables local IRQs while held, so
  a section is atomic against both other CPUs *and* this CPU's own ISRs — the ISR
  can't re-enter and self-deadlock).
- **`arch/x86/percpu.{c,h}`** — `cpu_t` per-core block (index, LAPIC id, online,
  `current`, `idle_task`, `slice_left`, kstack, tss). `this_cpu()` resolves the
  running core by its LAPIC ID (CPU 0 before SMP/LAPIC are up, so the single-core
  path is unchanged). `smp_register_cpu()` / `smp_set_bsp_lapic_id()`.
- **`kernel/sched.c`** — `current`/`idle_task`/`slice_left` moved from file-static
  globals to `this_cpu()->…` via local macros (zero churn in the scheduler body).
  `sched_init()` registers the BSP; its real LAPIC ID is patched in after the APIC
  switchover.
- **`arch/x86/lapic.c`** — `lapic_get_id()`, IPI senders (`lapic_send_init`,
  `lapic_send_sipi`, `lapic_ipi`) via the ICR, and `lapic_timer_start_this_cpu()`
  (reuses the BSP-calibrated periodic count) — all for M29-2/3.
- **Fine-grained locks added** (uncontended single-xchg on one core): PMM
  (`mm/pmm.c`, bitmap+refcounts, split into `_nolock` cores to avoid recursion),
  heap (`mm/heap.c`), page cache (`mm/pagecache.c`), IPC (`kernel/ipc.c`), pipes
  (`kernel/pipe.c`, wakes moved outside the lock), block I/O (`fs/block.c`,
  serializes the polled virtqueue/AHCI/NVMe path), VFS mount table (`fs/vfs.c`),
  keyboard buffer + modifiers (`drivers/keyboard.c`, IRQ-context safe).
- **Deferred to M29-3** (coupled to the AP scheduler entry): proc-table /
  scheduler locking and TLB shootdown — done together with how APs schedule.

Verified: selftest still green; both boot paths unchanged; `[APIC]`/`[TSC]` markers
and the heap large-alloc self-test all pass under `-smp 2`.

## M29-2 — AP bring-up (done)

The application processors are started and run kernel code; for now they park
(M29-3 makes them schedule).

- **`boot/ap_trampoline.asm`** — a flat binary (`org 0x8000`, assembled `-f bin`
  and wrapped into an object via `objcopy -I binary`). A SIPI starts each AP in
  16-bit real mode at `0x8000`; the trampoline goes real → protected → long mode
  on the **BSP's kernel CR3** (which maps both the low identity, where the code
  lives, and the high half, where C runs), then jumps to `ap_entry` on a per-AP
  kernel stack. The BSP publishes CR3 / stack / entry in a fixed parameter block
  at `0x8F00`; APs are started one at a time so the shared page is race-free.
- **`kernel/smp.c`** — `smp_init()` copies the trampoline to `0x8000` (safe: the
  PMM manages RAM from 1 MiB up, so it never hands out `0x8000`), registers each
  ACPI CPU in `g_cpus[]`, allocates a 16 KiB kernel stack per AP, and sends
  INIT-SIPI-SIPI (delays via the M28-3 `ktime_us()` clock), waiting for each AP to
  flag itself online. `ap_entry()` enables its Local APIC
  (`lapic_enable_this_cpu()` — per-CPU MSR + SVR, the MMIO is already mapped),
  loads the shared IDT (`idt_ap_load()`), marks online, and parks (`hlt`).
- **`arch/x86/lapic.c`** — ICR-based `lapic_send_init` / `lapic_send_sipi`;
  `lapic_get_id` / `lapic_enable_this_cpu`.

Verified (no `[EXC]`): `-smp 2` → `[SMP] online cpus=2`; `-smp 4` → all four
(`lapic_id=1,2,3` online + BSP). Single-CPU and the full selftest unchanged.

## M29-3 — APs run the scheduler (done) — **multicore achieved**

User code now runs on more than one core in parallel.

- **Per-CPU GDT/TSS/IST** (`arch/x86/tss.c`): `tss_setup_ap()` builds each AP its
  own GDT + TSS (own `rsp0` + IST stacks) so a ring-3→ring-0 entry on that core
  lands on that core's kernel stack. The GDT build was refactored into a shared
  `build_and_load_gdt()` used by both the BSP and the APs. `tss_set_kernel_stack()`
  now updates `this_cpu()->tss` (the BSP falls back to the global TSS).
- **Per-CPU idle task** (`kernel/smp.c`): `ap_entry()` installs a ring-0 idle task
  as the AP's `current`/`idle_task`, starts its LAPIC timer, and runs the idle
  loop. The timer tick preempts idle to a user task pinned to this core and
  returns here when that task blocks/exits.
- **Process CPU-affinity** (`kernel/process.c`): each process is pinned
  round-robin to an online CPU at creation/fork (`cpu_affinity`). `pick_user()`
  (`kernel/sched.c`) only considers tasks pinned to the running core, so two cores
  never run the same task and the context switch stays lock-free.
- **Process-table spinlock** (`kernel/process.c`): `proc_lock` guards the table,
  `next_pid` and the affinity rotor; `process_foreach()` holds it across the whole
  scan (the scheduler's callbacks only read/write process fields, never re-enter
  the lock). `process_reap_one()` detaches a ZOMBIE under the lock before it is
  freed, and only the zombie's affinity CPU reaps it — and only from its idle loop,
  once it has switched off the zombie's kernel stack — so a freed PCB/stack is
  never touched by another core.
- **TLB shootdown — not needed in the pinned model.** A user address space runs on
  exactly one core, so its page-table edits (demand fault, COW, mmap/mprotect/
  munmap, fork) and the `invlpg`/CR3 reload are all local to that core; no other
  core caches its mappings. The only shared kernel mapping that grows,
  `vmm_extend_physmap()`, is touched solely at boot/driver-bind time on the BSP
  (the runtime fault path uses the already-complete physmap), so no cross-core
  shootdown is required. Documented rather than implemented.

**Verified** (no `[EXC]`, no PMM leak):
- `-smp 2`, M8 workload: ring-3 tasks (pid 2,4,6,…) scheduled on **CPU 1**
  (`[SMP] cpu=1 run pid=…`), `[M8] PMM stable … NO LEAK`, `[M8] DONE`.
- `-smp 4`, M19 COW-fork demo: the forking child runs on an AP and the demo
  completes (`[M19] DONE`) — fork/COW is correct across cores.
- `-smp 1` and the full selftest unchanged; both boot paths green.
- selftest gained an M29 section (AP online + user-task-on-AP + no-leak + no-EXC).

**Phase I complete** (ACPI → APIC → TSC → SMP). Known follow-ups: load balancing
(affinity is static round-robin, no migration); per-CPU run queues (currently one
shared proc table under a lock — fine at these core counts); IPI-based reschedule
so a wake on another core preempts immediately instead of at the next tick.

### Post-ship fix — M5 kernel-stack race (found by `stress 16` on real VMware)

`stress 8` ran clean on VMware (multicore confirmed on hardware), but `stress 16`
panicked: `[M2][PANIC] vmm_map failed (-3 / already mapped)`. The TLB-shootdown
analysis above ("user spaces are per-CPU, so kernel-PT edits are boot-only") missed
**one** runtime shared-kernel-PT mutation: the **M5 per-process kernel stack**. All
32 slots live in a single shared 2 MiB kernel region (one page table), and
`vmm_alloc/free_kernel_stack_for_slot` (`mm/vmm.c`) map/unmap them on *every*
process create/destroy. Under SMP those race — the spawning core maps a slot while
a pinned core reaps another and unmaps its slot, corrupting the shared page table
and leaving a stale-present PTE → the next slot map hits `-3`. Fix: a dedicated
`kstack_lock` (irqsave) serializes those two functions. No shootdown needed (a
slot's kstack VA is only ever touched by the one core running that process).
Verified: `stress 16`/`stress 32` (48 procs create/destroy across 4 cores) run
clean, no PANIC/`[EXC]`, memory back to baseline (no leak). selftest 165/165.

**Lesson:** "kernel page-table edits are boot-only" was *almost* true — the
per-process kernel stack is the exception. Any future runtime kernel-VA map/unmap
(e.g. a vmalloc-style allocator, on-demand kernel buffers) must take `kstack_lock`
(or a shared kernel-PT lock) and, if the VA can be touched by another core, an IPI
TLB shootdown.
