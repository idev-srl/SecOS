# M25 — Anonymous pipes + console TTY + TCP throughput

_Status: code complete, build clean, pipe demo verified non-interactively
(`M25_PIPE_DEMO`). TTY cooked mode wired but verified interactively (not in the
debugcon selftest). Combines roadmap Option 1 (TCP throughput) and Option 3
(pipes + TTY) into one milestone._

## Scope

Three pieces shipped together:

1. **TCP throughput** — raise the window/RTT ceiling and absorb RX bursts.
2. **Anonymous pipes** — `SYS_PIPE` + a kernel ring-buffer object, blocking
   read/write, EOF/EPIPE, fork-inherited, demo across `fork()`.
3. **Console TTY** — cooked-mode line discipline (echo, backspace, Ctrl-D EOF,
   Ctrl-C line-cancel) for ring-3 stdin (fd 0) and `/dev/tty` / `/dev/console`.

## Part A — TCP throughput

- `net/tcp.c`: `TCP_RXBUF` / `TCP_TXBUF` 8192 → **65536**. The advertised receive
  window is `min(TCP_RXBUF - rx_len, 65535)`, and 64 KiB is the largest window
  expressible **without the window-scaling option** — so this is the single
  biggest lever on the `window / RTT` throughput ceiling (~8× headroom over the
  old 8 KiB). Cost: 16 conns × 128 KiB ≈ 2 MiB static BSS.
- `drivers/e1000.c`: `RX_DESC` 64 → **256**, `TX_DESC` 16 → **64**.
- `drivers/e1000e.c`: `E1000_RX_DESCS` 32 → **256**, `E1000_TX_DESCS` 32 → **64**.
  Deeper rings absorb more packets between the timer-tick polled drains, reducing
  drops at high rate. (RDLEN stays 128-byte aligned: 256×16=4096, 64×16=1024.)

These are localized constant bumps; no logic change. Re-measure on real VMware
(host: `python3 -m http.server`, VM: `nettest <hostip> 8000 /big.bin`).

## Part B — Anonymous pipes

**New files** `kernel/pipe.{c,h}`: a `pipe_t` is a 4 KiB ring buffer with reader
and writer reference counts, from a static pool of 16. The API is non-blocking —
`pipe_read`/`pipe_write` return `-2` ("would block") and blocking is layered on
top in the syscall trap:

- `pipe_read`: `>0` bytes; `0` = EOF (drained **and** `writers==0`); `-2` if empty
  but a writer is still open.
- `pipe_write`: `>0` bytes (short write allowed); `-1` = EPIPE (`readers==0`);
  `-2` if full but a reader is still open. Each successful op calls
  `sched_wake_pipe()` to wake the peer.

**fd table** (`proc_fd_entry`) gained `is_pipe` + `pipe_w`; when `is_pipe`, `inode`
holds the `pipe_t*`. `SYS_PIPE` (31) allocates a pipe and two fds (read end +
write end) and copies the pair out. `ksys_read`/`ksys_write` branch to the pipe
path; the read end rejects writes and vice-versa.

**Blocking** is handled in `kernel/syscall_trap.c` exactly like M16/M17: a pipe
read/write that returns `-2` arms `process_t.wait_pipe`, rewinds `rip`, and calls
`sched_block_current()`; `sched_wake_pipe(pp)` (new, modelled on
`sched_wake_chan`) flips every task blocked on `pp` back to READY, and it re-runs
the syscall and re-checks (a spurious wake just re-blocks).

**Refcounts across fork/close/exit**: `fork` shallow-copies the fd table, so
`process_fork` bumps each inherited pipe end's count (`pipe_ref`). `close` and
`process_destroy` drop the count (`pipe_unref`), which wakes the peer (so the
reader sees EOF / the writer sees EPIPE) and frees the object once both ends are
gone.

### The fd 0/1/2 collision bug (found + fixed during bring-up)

First demo run **deadlocked**: a fresh process had **no** fds open, so `pipe()`
returned fds **0** (read end) and **1** (write end). The write end (fd 1) hit the
`fd==1` console special-case in `ksys_write` (so "M25-PIPE-OK" printed to the
console instead of the pipe), and the read end (fd 0) hit the new `fd==0` →
`tty_read` path, blocking the child on the keyboard forever.

**Fix**: `process.c` now reserves fds 0/1/2 as stdin/stdout/stderr at process
creation (`used=1`, no inode — the std-stream paths are keyed on the fd number),
so `open()`/`pipe()` allocate from fd 3 up. This is the right POSIX shape anyway.

**libc**: `pipe(int fds[2])`. **Demo** `user/m25_pipe.c` (gate `M25_PIPE_DEMO`):
parent `pipe()`+`fork()`, parent writes "M25-PIPE-OK" down the write end and
closes it; the child blocks on the read end, prints the bytes, then reads again
and gets EOF. Verified: `[m25] child read: M25-PIPE-OK` / `[m25] child got EOF OK`
/ `[m25] DONE-USER` / `[M25] DONE`, no `[EXC]`.

## Part C — Console TTY (cooked line discipline)

**New file** `kernel/tty.c` — `tty_read(buf, len)`: a cooked-mode line read used by
ring-3 stdin (fd 0, special-cased in `ksys_read`) and the devfs `DEV_CONSOLE`
read path (`/dev/tty`, `/dev/console`). It line-buffers input, echoes typed
characters, and handles:

- **Enter** (`\n`/`\r`): echo newline, deliver the line including the `\n`.
- **Backspace** (`\b` / DEL `0x7f`): erase the last char (`"\b \b"`).
- **Ctrl-D** (`0x04`): EOF — returns `0` on an empty line, else delivers the
  partial line.
- **Ctrl-C** (`0x03`): echoes `^C`, discards the line, returns `-1` (interrupted).

Leftover that doesn't fit the caller's buffer is preserved for the next read. A
single static line buffer is sufficient because only the foreground process reads
stdin at a time (the shell blocks in `SYS_WAIT` while a child runs).

**Blocking model**: like the socket layer, `tty_read` spins on `sti; hlt` so the
keyboard IRQ (and the timer-driven USB-HID poll) can fill the shared keyboard
buffer while waiting — the INT 0x80 gate is an interrupt gate (IF cleared on
entry), so interrupts must be re-enabled to ever wake.

**Deferred**: Ctrl-C only interrupts an in-progress *read*. Turning it into an
asynchronous kill of a compute-bound foreground process needs a real
signal-delivery mechanism (SIGINT + handler tables) — that is the Phase G/L
signals work and is intentionally out of scope here.

## Open follow-ups

- TCP **window scaling** would lift the window past 64 KiB for high-BDP links.
- Pipe **`SIGPIPE`** (today a write to a reader-closed pipe returns -1/EPIPE; no
  signal) — needs the signal subsystem.
- TTY **raw mode** / termios-style control, and async **Ctrl-C → SIGINT** kill of
  a compute-bound foreground process (signal delivery).
- Shell **pipelines** (`cmd1 | cmd2`) now that pipes + fork + exec exist.
