# M15 — Fault-driven process termination

**State:** done. Self-test harness **66/66** (was 61/61; +5 M15 assertions).
Demo gated behind `M15_KILL_DEMO`, off by default. First milestone of Phase F
(robustness & process model) from `docs/ROADMAP_TO_COMPLETE_OS.md`.

## Goal

Stop letting a buggy user program take down the whole machine. Before M15, an
unhandled CPU exception in **any** context — including a ring-3 process doing a
wild memory access — printed `[EXC]`/`[PANIC]` and **halted the kernel**
(`while(1) hlt`). A complete OS must contain a faulting process: terminate it and
keep scheduling.

## What landed

### Page-fault handler returns instead of halting — `mm/vmm.c`
`vmm_handle_page_fault` is now `int` (`0` = serviced/retry, `-1` = genuine
violation) and **never halts**. On the unhandled path it emits a terse decoded
debugcon line (`[PF] UNHANDLED ... (protection,write,user)`) and returns `-1`;
the framebuffer panic UI and the `while(1) hlt` are gone from here — that
decision moves up to the exception handler.

### Centralized kill-vs-panic decision — `kernel/panic.c`
`exception_handler` already had the trapframe (`regs`). It now:
- For #PF: calls `vmm_handle_page_fault`; on `0` returns (demand-paged), on `-1`
  falls through to the shared termination logic.
- For any exception `< 32`: reads the saved `cs`. **`(cs & 3) == 3` ⇒ the fault
  happened in ring-3** ⇒ the offending *process* is at fault, not the kernel:
  log `[EXC] ring3 fault -> kill pid=N` and call `sched_kill_current(int_no)`
  (noreturn). A **ring-0** fault is a real kernel bug ⇒ the original panic UI +
  halt is preserved.

The `[EXC]` debugcon line now carries `ring3`/`ring0` so logs are unambiguous.

### The kill path — `kernel/sched.c`
`sched_kill_current(int reason)` mirrors `sched_exit_current` (the SYS_EXIT path)
but is driven by the exception handler: it marks `current` `PROC_ZOMBIE`, records
a **signal-style exit status** (`128 + vector`, à la POSIX), picks the next
runnable task with the existing `pick_user`, and `switch_to`s into it — never
returning. The dead task is reaped later by `sched_reap_zombies` from the next
scheduling context (idle), exactly like a normal exit. If there is no killable
current (idle/none), the fault is unrecoverable and we halt (genuine kernel bug).

Reusing the SYS_EXIT machinery means the kill is **zero new teardown code**:
`process_destroy` → `vmm_space_destroy` already frees the address space and (since
M14) every faulted leaf frame, so a killed process leaks nothing.

### Exit status field — `kernel/process.{h,c}`, `kernel/sched.c`
`process_t` gains `int exit_code` (0 = normal SYS_EXIT, `128+vec` = killed by a
fault). Initialized at creation; set on both exit and kill. This is the seed of
M16's proper `wait`/exit-status plumbing.

### Demo + harness — `kernel/kernel.c` (`M15_KILL_DEMO`), `user/crashtest.c`
A new signed `crashtest` does a wild write to NULL (address 0 hits the supervisor
low-identity map ⇒ a ring-3 **protection** fault, unhandled). The demo idle task
spawns it, the kernel kills it (`[KILL] pid=1`), and `crashtest`'s post-fault
`STILL ALIVE` line **never prints**. The demo then spawns the signed `hello`,
which runs normally — proving the scheduler/kernel survived. Five assertions
added; note the M15 run **intentionally** contains `[EXC]`, so (unlike other
milestones) M15 does not assert its absence — liveness is proven by the later
program running and `[M15] DONE`.

## Things worth noting

- **Why `cs`, not the error-code U/S bit:** the saved `cs` is the privilege of
  the *faulting instruction*. The PF error-code U/S bit can be `0` (kernel) even
  for a process's bug when the kernel touches a bad user pointer inside a syscall.
  Keying the kill on `cs == ring3` is the precise "the user program did this"
  signal. (See deferred below for the kernel-mode-bad-pointer case.)
- **IST stacks:** #PF runs on IST2; other exceptions on the kernel stack. The kill
  abandons that stack via `arch_iret_to_tf` into the next task — identical to how
  preemption (`isr_timer`) and SYS_EXIT already abandon their stacks. The IST is
  reloaded fresh from the TSS on the next fault, so nothing grows.
- **NULL is "present":** writing to address 0 from ring-3 is a *protection* fault
  (the low-identity map is present but supervisor), not a not-present fault — so
  the demand-paging fast path correctly skips it and it routes to the kill path.

## Deferred / next (Phase F)

- **Kernel-mode fault on a bad user pointer in a syscall** still panics (ring-0
  `cs`). The clean fix is a fault-tolerant `copy_from/to_user` (a
  fixup/`set_thread_fault` mechanism) that returns `-EFAULT` instead of faulting
  — a hardening item, not M15's scope.
- **Exit status delivery:** `exit_code` is recorded but `SYS_WAIT` still returns
  only running/done. **M16** wires argv/env + exec + blocking `wait` carrying the
  status (incl. the killed-by-signal encoding).
- **Signals to the process** (catchable) — only fatal termination exists today.
